为什么 v1 不直接写 Daemon？

两条路线最终都调用同一个 OPC CLI；差别在于谁承担调度系统的责任。

现在选 A · 保留迁移到 B 的能力

A · GitHub Actions 调度

v1 推荐
1
GitHub 接收事件Ready label 立即触发；定时 sweep 补漏。
↓
2
GitHub 管理运行排队、并发限制、运行历史与 job-scoped token。
↓
3
官方 Runner 接单Mac mini 只需维持一个成熟的 runner service。
↓
4
调用 OPC CLI核心状态机完成 claim、execute、verify、recover、publish。

我们只维护

业务状态机Issue schema验证规则恢复策略
Runner 离线任务仍留在 GitHub 队列和运行记录中；恢复上线后继续处理，24 小时边界清晰可见。

B · 直接写 Mac mini Daemon

未来备选
1
自己接收事件选择轮询，或运营一个可从公网访问的 webhook。
↓
2
自己实现调度器队列、租约、并发、重放、幂等、补漏和优先级。
↓
3
自己运营服务launchd 只能重启进程；逻辑卡死、凭证过期仍需额外 watchdog。
↓
4
再调用 OPC CLI核心执行能力并没有因此减少。

除了核心逻辑，还要维护

Poller / WebhookQueueLease storeCredential vaultWatchdogLog retentionUpdater
Daemon 失效负责发现任务的组件本身消失；如果没有第二套监控，系统可能安静地停止，而你不会收到结果。

关键折中：把可迁移能力放在 OPC CLI，不放在自建 daemon

今天GitHub Actions adapter
→
稳定的 OPC CLIclaim · execute · verify · recover · publish
←
未来需要时Daemon adapter
所以 A 不是“多一层”

它是把通用调度责任交给现有平台，让我们只构建有产品价值的部分。对“不要我监控过程”这个目标，少运营一个自建常驻服务比少写几段 workflow YAML 更重要。

什么时候切到 B？

只有当 Actions 的队列、鉴权、跨组织或调度限制已经成为可测量的阻碍，再替换 adapter；核心 CLI 不需要重写。
